## 2. 구현 전 질문과 확정 정책

| 질문 | 필요한 이유 | 달라질 구현·검사 |
| --- | --- | --- |
| 우선 부서는 어디이며 각 부서는 지급 후 몇 대를 남겨야 하는가? | 우선이라는 말만으로 비교 조건을 결정할 수 없음 | Service 분기, 각 부서의 동일 수량·최대 허용 수량 검사 |
| 부서를 생략하거나 지원하지 않는 값을 보내면 어떻게 처리하는가? | 기존 호출 호환과 잘못된 입력의 구별 필요 | 선택적 쿼리 기본값, Literal 검증, 생략 성공과 미지원 422 검사 |
| 이 API는 조회만 하는가? 초과·0·음수·없는 장비 처리는 유지하는가? | 판단 변경과 실제 지급 범위를 구분 | 재고 불변·422·404·초과 불가 검사 |

질문 검토용 프롬프트(작성했으나 Claude에 미전송):

```text
담당자가 특정 부서에 우선 배정이 필요하다고 했어.
내 질문은 ① 우선 부서와 예비 수량 ② 부서 생략·미지원 값 처리 ③ 조회 범위와 기존 오류 처리야.
빠진 중요한 조건을 검토하고 구현 전에 꼭 확인할 질문을 골라줘.
미확정 정책은 추측하지 말고 파일 수정이나 명령 실행도 하지 마.
```

확정 정책은 과제에 명시되어 있다. `it`·생략은 `1 <= quantity <= available`, `general`은 `1 <= quantity < available`이다. 미지원 부서·0·음수 수량은 422, 없는 장비는 404, 재고 초과와 재고 0은 200/false. 조회는 데이터를 바꾸지 않는다.

## 5. 구현과 diff 확인

- Router: `department: Literal["it", "general"] | None = Query(default=None)`을 받아 Service에 전달. 생략은 None이고 빈 문자열·기타 값은 422.
- Service: `department: str | None = None`으로 기존 두 인자 호출도 유지. `general`이면 `<`, 그 외 유효한 API 입력은 `<=`.
- 새 검사: `tests/test_department_availability.py`.
- 활동 기록: `logs/02.md`.
- `git diff --check` 통과. 기존 추적 구현 diff는 Router 10줄, Service 6줄 변화이며 새 테스트는 `git status`로 찾아 직접 읽었다.
- `git diff 5934b2f -- app/data.py app/schemas.py tests/test_equipment.py checks/check_availability_contract.py requirements.txt` 출력 없음. 데이터·응답 모델·기존 검사·의존성 명세를 변경하지 않았다.
- Service는 내부 함수로, 미지원 department 거절은 HTTP Router에서 보장한다. 내부 함수를 직접 호출하는 별도 공용 API 계약은 이번 범위에 없다.

## 8. 결과 설명과 한계

1. 부서별 판단은 Service의 `check_availability`에서 한다. Router는 입력 검증과 전달을 맡는다.
2. 모든 부서에 동일한 `<` 또는 `<=`를 무조건 적용하면 양쪽 정책을 만족하지 못한다. 부서에 따라 비교를 달리해야 한다.
3. `test_department_policy[1-3-3-True-False-general]`이 일반 부서까지 IT처럼 허용하는 구현을 검출한다.
4. 테스트 외에도 Swagger 실제 응답, 반복 HTTP 조회 후 재고 불변, 데이터·기존 검사 변경이 없는 diff를 확인했다.
5. 조회는 그 시점의 판단일 뿐 예약이나 지급 확정이 아니다. 부서 정책만으로 다른 직원과의 동시 지급 경쟁을 막을 수 없다. 지급 보장이 필요하면 별도 예약/지급 API, 영속 데이터, 트랜잭션 안에서 재고 확인·차감을 원자적으로 처리하는 장치가 필요하다. 이번에는 구현하지 않았다.
6. 아직 검사하지 않은 조건: 대규모 동시 요청·부하, 중복 쿼리 키, 장비 ID 형식 오류 등. 실제 지급 동시성은 현재 조회 전용 범위 밖이다.

기능 구현·로컬 검증 완료. 전체 제출 절차는 Claude 재인증 후 수업 활동 재수행, 인적사항 확인, GitHub 게시·교사 접근 확인이 남았다. 최종 로컬 커밋 ID는 LMS 워크시트에 기록한다.
