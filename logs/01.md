## 1. 탐색 프롬프트와 후속 질문

실제로 Claude CLI에 전달한 요청:

```text
이 저장소의 CLAUDE.md를 읽고 GET /equipment/1/availability?quantity=3 요청을 조사해줘.
app, tests, checks 범위에서 진입점, Router-Service 호출, 데이터 출처, 수량 조건,
기본 검사와 별도 검사의 차이를 파일과 함수 근거로 표로 정리해줘.
직접 실행한 기본 검사는 3 passed, 별도 검사는 같은 수량에서만 1 failed, 3 passed였어.
후속 확인: quantity=4와 비교하고 Availability가 직접 호출하는 함수인지 응답 모델인지 구분해줘.
파일 수정, 명령 실행, 커밋은 금지한다. Read, Glob, Grep만 사용하고 실제 읽은 파일을 밝혀줘.
```

실제 호출은 `claude -p`에 `--tools 'Read,Glob,Grep' --allowedTools 'Read,Glob,Grep' --strict-mcp-config --output-format stream-json --verbose`를 사용했다.

결과: `Failed to authenticate: OAuth session expired and could not be refreshed`.
Claude의 Read/Search 도구 기록과 분석 답변은 확보하지 못했다. 이하 분석은 Codex가 파일을 직접 읽어 확인한 대체 수행 기록이다. 후속 질문은 위 요청에 포함했으며 별도 Claude 후속 대화는 실행하지 않았다.

실제로 읽은 파일: `CLAUDE.md`, `README.md`, `requirements.txt`, `app/main.py`, `app/routers/equipment.py`, `app/services/equipment_service.py`, `app/data.py`, `app/schemas.py`, `tests/test_equipment.py`, `checks/check_availability_contract.py`, 기존 `logs/01.md`, 제공 워크시트.

## 2. 코드 지도와 핵심 근거 확인

| 파일 / 함수 | 역할·코드 근거 | 먼저 확인할 부분 |
| --- | --- | --- |
| `app/main.py` / `app`, `health` | FastAPI 생성 후 `app.include_router(router)`로 장비 Router 등록 | 진입점과 Router 연결 |
| `app/routers/equipment.py` / `check_availability` | `quantity: int = Query(ge=1)`로 검증하고 `equipment_service.check_availability(equipment_id, quantity)` 호출 | 인자 전달·404 분기 |
| `app/services/equipment_service.py` / `check_availability` | `EQUIPMENT.get(equipment_id)` 조회, `available_quantity`를 읽고 비교 | `quantity < available` |
| `app/data.py` / `EQUIPMENT` | 1번 재고 3, 2번 재고 0인 메모리 사전 | 비교값의 실제 출처 |
| `app/schemas.py` / `Availability` | `response_model`로 등록한 응답 모델, 네 응답 필드 정의 | 업무 판단 함수와 구분 |

| 분석 | 직접 확인한 근거 | 판단 |
| --- | --- | --- |
| Router가 Service에 ID와 수량을 전달한다 | Router의 실제 호출문과 Service의 두 매개변수 일치 | 수용: 함수 이름 나열이 아니라 호출 코드로 연결 확인 |
| 동일 수량 거절의 원인은 미만 비교다 | 데이터의 재고 3과 Service의 `quantity < available`에 3을 대입하면 False | 수용: HTTP 재현과 완료 조건 실패가 일치 |
| Schema가 지급 가능 여부를 계산한다 | `Availability`에는 네 필드만 있고 비교 연산은 Service에 있음 | 이 설명이라면 수정해야 함. 실제 Claude 제안은 아님 |

요청 흐름: HTTP 경로 ID `1`·쿼리 `3` → FastAPI 정수·최솟값 검증 → Router → Service → `EQUIPMENT[1]`의 재고 `3` → `3 < 3`은 False → 네 필드 사전 → `Availability` 응답 검증·직렬화 → HTTP 200.
수량 4라면 `4 < 3`도 False이다. 없는 장비는 Service의 None을 Router가 404로 변환한다.

## 3. 분석 후 판단

- 탐색을 줄인 부분: 해당 요청의 Router·Service·데이터·응답 모델과 두 검사 파일로 범위를 좁혔다. DB·예약 기능은 없다.
- 가설: 예비 장비가 필요 없는 업무 정책은 `quantity <= available`인데 코드는 `<`를 사용한다.
- 코드상 예상과 실제 관찰: 재고 3에 요청 3은 False, 요청 4도 False였으며 HTTP 응답과 일치한다.
- Redis 설명 확인: `app/`와 `requirements.txt`에서 Redis 검색 결과 없음. Service가 `app.data.EQUIPMENT`를 직접 사용하므로 이 경로에서 Redis를 사용한다는 설명은 근거가 없다.
- 초기 테스트는 health, 장비 목록, 재고 미만 요청만 검사한다. 작성자의 의도나 정책 이해 수준은 테스트만으로 단정할 수 없다.

## 4. 수정 전 관찰

원본 프로젝트에서 현재 작업 폴더를 맞춰 실행했다. 아래 `python`은 이번 작업의 `work/venv/bin/python`을 의미하며, 제출받은 환경에서는 가상환경을 활성화한 뒤 같은 명령을 사용한다.

```text
python -m pytest -q
3 passed, 1 warning in 0.14s

python -m pytest checks/check_availability_contract.py -q
FAILED checks/check_availability_contract.py::test_availability_contract[1-3-3-True]
{'can_allocate': False} != {'can_allocate': True}
1 failed, 3 passed, 1 warning in 0.16s
```

처음 프로젝트 밖에서 tests의 절대 경로만 지정한 시도는 `ModuleNotFoundError: No module named 'app'`로 1 collection error였다. 이는 업무 버그가 아니라 작업 디렉터리 문제였다. 프로젝트 폴더에서 다시 실행해 위 결과를 얻었다.

실제 Uvicorn 서버를 `127.0.0.1:8765`에서 실행하고 HTTP GET으로 확인했다. 8000 대신 별도 포트를 사용했다. 이 표는 Swagger 예시가 아닌 실제 서버 응답이다. 수정 전 Swagger의 Try it out 조작은 미실행이다.

| 장비 ID | 재고 | 신청 | 기대 can_allocate | 수정 전 실제 | HTTP |
| --- | --- | --- | --- | --- | --- |
| 1 | 3 | 1 | true | true | 200 |
| 1 | 3 | 3 | true | false | 200 |
| 1 | 3 | 4 | false | false | 200 |
| 2 | 0 | 1 | false | false | 200 |

동일 수량 응답 본문:

```json
{"equipment_id":1,"requested_quantity":3,"available_quantity":3,"can_allocate":false}
```

별도 검사 파일은 `check_`로 시작해 기본 pytest 파일 수집 패턴에 포함되지 않는다. 경로를 직접 지정해야 한다. 이미 통과한 초과·재고 0·수량 0 검사는 수정 후 회귀를 방지한다.

## 5. 변경 판단

검토한 최소 계획: Service의 비교 연산자만 `<`에서 `<=`로 변경한다. 데이터·기존 테스트·응답 필드·Router·함수 이름은 유지한다. 실제 지급·예약·DB는 추가하지 않는다.

수정 요청 문안(Claude 인증 실패로 미전송, Codex가 이 범위로 수행):

```text
재고 3에 quantity=3인 요청이 실제 False지만 업무상 True여야 한다.
Service의 비교 조건만 최소 수정해줘. 초과 수량과 재고 0은 계속 False여야 한다.
장비 데이터와 tests/checks의 기존 검사는 변경하지 마.
기본 검사와 별도 완료 조건 검사를 실행하고 명령·실제 결과·diff를 보고해줘.
```

승인 판단: 3 <= 3은 True이고 4 <= 3과 1 <= 0은 False이다. 기존 입력 검증은 건드리지 않는다. 데이터 수량이나 테스트 기대값을 바꿀 이유가 없다.

## 6. 수정 후 검증

```text
python -m pytest -q
3 passed, 1 warning in 0.13s
python -m pytest checks/check_availability_contract.py -q
4 passed, 1 warning in 0.13s
python -m pytest tests checks/check_availability_contract.py -q
7 passed, 1 warning in 0.13s
```

경고는 설치된 Starlette TestClient의 httpx 사용 중단 예정 경고이며, 실패가 아니다. 과제의 의존성 변경 금지 범위를 지켜 패키지 명세를 바꾸지 않았다.

`git diff --check` 통과. 구현 diff:

```diff
-    can_allocate = quantity < available
+    can_allocate = quantity <= available
```

서버를 재시작한 후 같은 네 HTTP 요청의 결과는 순서대로 `true, true, false, false`, 모두 200이었다. 같은 수량 응답은 `{"equipment_id":1,"requested_quantity":3,"available_quantity":3,"can_allocate":true}`이다. 재고·응답 필드는 그대로다.

기본 단계에서 변경한 추적 파일: `app/services/equipment_service.py`, `logs/01.md`. 새 테스트 파일 없음. 코드 한 줄 외에는 활동 기록만 변경했다. 이후 추가 실습의 diff와 테스트 수는 `logs/02.md`에서 따로 기록한다.
